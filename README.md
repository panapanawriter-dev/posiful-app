# 弁当訪問販売支援アプリ

余剰在庫を活用しながら、
直近日替わりメニューとは「代わり映え」のある
日替わり弁当を提案するアプリです。

## 試作版の主な機能

- レシピ登録
- AIによるレシピ構造化
- メニュー特徴の生成
- レシピのベクトル化・保存
- 材料からメニュー検索
- ベクトル類似度を利用した「代わり映え」ランキング
- 日替わり変更後の在庫消費量の表示

## 実装した試作

Streamlit + Python + Supabase PostgreSQL / pgvector を使用。
`C案要件定義書.docx`、`C案ER図解説書.docx`、FigmaのC案に沿った構成です。
`PROJECT_ZERO_w1-4/2_main_PROJECT_ZERO` のStreamlit画面、DB層の分離、
コサイン類似度によるランキングを参考にしています。

### 起動（PowerShell）

```powershell
# 初回のみ。Python 3.12以上を使用
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.lock.txt

# 起動
.venv/Scripts/python.exe -m streamlit run app.py --server.address 127.0.0.1
```

この作業環境には `.venv` を作成済みです。
デモモードは外部APIなしで、材料検索、ランキング、単位換算、
消費量・残量・不足量表示を試せます。デモの在庫・販売個数は起動日のサンプルです。
デモベクトルは手作りの仮データで、AIによる意味的な品質は評価していません。
デモで追加したレシピはセッション内のみ保持します。

### Supabase

専用プロジェクト `posiful-app` を組織 `techyuta`、東京リージョンに作成済み。
プロジェクトID: `dklpsxmjbhmgertlbnhc`。

[Supabaseダッシュボード](https://supabase.com/dashboard/project/dklpsxmjbhmgertlbnhc)

`supabase/schema.sql` の7テーブルと2つのRPCを適用済みです。
別の新規環境にはこのSQLを適用してください。既存テーブルがあるDBへの再実行は想定していません。
追加連携スキーマ `supabase/cloud_integration.sql` も専用プロジェクトへ適用済みです。別の新規DBには `schema.sql`、次に `cloud_integration.sql` の順に1回ずつ適用します。
すべてのテーブルでRLSを有効にし、自分が所属するワークスペースのデータだけを扱います。
公開キーとSupabase Authを使用し、service_roleキーは使用しません。

1. `.env.example` を `.env` にコピーし、URLと公開キーを設定します。この作業環境では設定済みです。
2. 画面左の「接続設定」でSupabaseを選択。「アカウント登録」でメール・パスワードを入力し、確認メールのリンクを開いてログインします。
3. 所有者は「サンプルをSupabaseへ移行」を1回実行。10レシピ・7材料の在庫・10社・220件の販売履歴・10月予定がDBへ保存されます。既存データは上書きしません。
4. 協力者は先にアカウント登録とメール確認だけ行います。サンプル移行はせず、所有者の「共同編集メンバー」でメールアドレスを招待してから再読み込み。同じデータを読み書きできます。
5. AIで新しいレシピを登録するときは `OPENAI_API_KEY` を各実行環境の `.env` に設定します。サンプル移行・販売予測・検索には不要です。

Supabaseモードではレシピ・在庫・販売履歴・予定をDBから読み込み、差し替え結果と変更履歴をDBへ保存します。予定の更新はリビジョン照合と行ロックで同時編集による上書きを防ぎます。画面の再実行・再読み込みで最新データを取得します。デモモードは引き続きローカルで利用できます。

移行するサンプルのEmbeddingは3次元の仮ベクトルを1536次元へゼロ埋めしたものです。AI生成ベクトルとはモデル名で区別します。移行後の検索時にはJSONファイルを読みません。JSONは初期移行の入力とデモ用に残しています。

登録時に検索特徴を生成し、1536次元Embeddingを保存します。
検索時には保存済みベクトルを比較し、API呼び出しは行いません。
登録全体は1つのDBトランザクションです。更新UIは今後の追加対象です。
セッション期限が切れた際は再度ログインします。

### 既存在庫・販売実績からの予測

C案の在庫管理は実装していません。追加要件として販売実績からの簡易需要予測を実装しました。
在庫は `inventory` のデータを参照します。想定販売個数は固定値や `menu_sales_estimates` の値を使わず、販売実績から計算します。
Table Editorから投入する場合、`user_id` に利用者のAuth UUIDを必ず設定してください。
`ingredient_id` / `menu_id` は同じ利用者が登録した材料・メニューのIDを使います。
企業別に販売食数の対数を目的変数とし、曜日・第1週・現場職の雨を説明変数とするリッジ回帰を学習します。
対象日より前の実績のみ使用し、サンプル生成時の通常数量・補正係数は学習に使用しません。
8件未満では同曜日平均（なければ全日平均）を使います。全社の予測を合計して材料消費量・残量を計算します。
土日は販売なしのため0食。対象日の天気は検索・詳細画面で指定します。
メニュー別の人気差は未学習で、新メニューにも同じ日付・天気の予測を使います。
販売実績が不足する企業がある場合は全体の予測を表示しません。
デモは2026年9月のローカルサンプル実績、SupabaseモードはDB内の販売実績を使用します。実績がない場合は未登録と表示します。
在庫の消費期限が販売対象日より前のものは計算から除外します。
g/kg、ml/Lは換算します。個数と重量など、互換性のない単位はエラーを表示します。

比較メニューは全企業共通の暫定日替わり予定から自動取得します。
指定材料を使用する候補だけを抽出し、最近のメニューのうち最も似たものとの
コサイン距離が大きい順に表示します。比較対象と異なるEmbeddingモデルは順位付けしません。
表示は採用時のシミュレーションであり、在庫の実データは更新しません。

2026年10月の暫定予定から、対象日の前後2暦日のメニューを自動選択します。
企業・比較期間の選択はありません。対象日自身は除外し、未来の予定も参照します。
土日は提供なしです。営業日で前後2日ではなく、カレンダー上の前後2日です。
`data/sample_menu_plan_2026_10.json` に1か月分の暫定予定を保存しています。

デモの変更は `data/menu_plan_changes.json`、Supabaseモードの変更はDBの `menu_plans` と `menu_plan_changes` に保存し、再読み込み・再起動後も反映します。
元のサンプル予定は保持します。変更後の予定は次の前後2日比較にも使います。
土日など提供予定のない日は差し替えできません。
SupabaseモードはDBの共有予定を参照します。未登録メニューは警告表示して比較から除外します。

### 1か月の提供履歴サンプル

`data/sample_history_2026_09.json` に2026年9月の22営業日×10社＝220件を保存しています。
社名は架空、すべてサンプルであることを明示しています。土日を除き、祝日は通常営業と仮定。
需要予測ではなく、検証用に作成した販売・提供履歴です。

- 青葉製作所・みなと物流: 水曜は一部部門が休みで通常の20%。
- ひかり商事・東都システム・さくら企画・北町サービス: 第1週（9/1〜9/7）は訪問・外出が多く通常の40%。
- 残り4社: 特別な減少なし。
- 曜日係数: 月85%、火100%、水95%、木110%、金80%。各社の基準販売数は12〜26食で、10社合計150〜250食の範囲に日別調整します。
- 日々の変動: ±8%。乱数シード固定で再生成できます。
- 架空の天気: 晴れ・曇り・雨。同一訪問エリアのため同日の10社は同じ天気です。
- 現場職3社（みなと物流・北町サービス・中央設備）は雨の日に1.3倍。
  販売食数は「通常時の食数×特別減少係数×天気係数」を四捨五入します。
  水曜休み・第1週の減少と雨の増加が重なるケースも含みます。

通常時の食数、販売食数、減少係数、減少理由を各行に保持します。

# 複数材料の希望消費量による候補検索

デモの営業規模は10社合計で1日150〜250食です。9月の販売履歴は企業別の曜日・休み・雨の係数を残し、日別の全体量をこの範囲に調整しています。販売予測と消費量はこの履歴に基づきます（予測値そのものを範囲に固定する処理はありません）。在庫は必要量の逆算を行わない固定値で、鶏もも肉90kg、玉ねぎ55kg、豚肉30kg、さば・鮭各15kg、にんじん5kg、じゃがいも7kg。鶏肉は多め、その他はおおよそ1週間分の目安です。希望消費量の初期値は20kgで、材料ごとに変更できます。

候補の材料表には希望消費量・予測消費量・差分を表示し、希望量への近さ／前後2日のメニューとの相違度／総合評価を独立表示します。総合評価順・相違度順・希望量への近さ順を切り替えられます。比較できる指標が片方だけの場合は「参考評価」と表示します。差し替えは詳細画面のボタンで人が決定します。

検索の対象日・天気に対応する販売予測を表示します。「レシピ一覧」の「指定日の販売予測」でも日付・天気を選び、10社合計と企業別内訳を確認できます。

「日替わりを探す」で材料を複数選び、それぞれの希望消費量と単位を入力できます。選択材料をすべて使い、前後2日の予定と同じメニューではない候補を表示します。

販売予測食数×1食あたりの材料量で消費量を計算します。材料ごとの近さは `1 / (1 + |予測消費量 - 希望量| / 希望量)` として平均し、前後2日のメニューとのコサイン距離を0〜1に換算した値と同じ重みで評価します。希望量の超過・不足はともに差として扱い、g/kgなどの単位は換算します。比較データがない場合は計算できる指標のみで並べ、画面に未評価を表示します。優先度は検索内の評価値で、販売の確率ではありません。
